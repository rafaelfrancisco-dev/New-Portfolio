# Portfolio security audit — 8 October 2026

**Target:** https://imaginarymakings.dev. **Source baseline:** `91b6136`. Production's exact deployed revision and binary build version were not available for verification.

**Conclusion:** No unauthenticated content-write or admin-authentication bypass was found in the reviewed routes. All 11 admin POST routes rejected anonymous requests, missing CSRF tokens, and foreign origins in isolated tests. However, the public login handler has two reproduced resource-exhaustion weaknesses, proxy trust is implicit, and password rotation does not revoke existing sessions. These should be addressed before treating the service as hardened.

This is an audit, not a deployment of fixes. Changes delivered here are the report, supporting evidence, a remediation plan, and opt-in local reproduction tests. Existing databases, credentials, application behavior, and production settings were not changed.

## Scope and evidence

Reviewed all application routes, authentication/session/CSRF logic, SQL and migrations, filesystem access and uploads, Markdown/templates/HTMX, Flickr OAuth/encryption/synchronization, DBOS startup, Docker/systemd/deployment helper, CI, and dependency configuration. Checked relevant Fuego and DBOS dependency implementations rather than assuming their defaults.

Public verification used a small number of GET requests, with no production credential attempts, uploads, content changes, load tests, or port scanning. Source-level attack reproductions ran against disposable SQLite databases through the real route table.

## Prioritized findings

### F01 — High: login parses attacker uploads before authentication without a total body limit

**Location:** `internal/handlers/admin.go:198–207`; compare the protected-route limit at `admin.go:129`.

`adminLogin` calls `r.FormValue("csrf_token")` before applying any `http.MaxBytesReader`. Go's form handling also accepts multipart bodies; its multipart memory threshold is not a total upload limit and larger file parts can spill to temporary storage. The protected admin middleware's 11 MiB limit does not apply to `/admin/login`.

**Reproduction:** an unauthenticated request with a fabricated CSRF cookie and invalid token caused a complete 12 MiB multipart file to be parsed before returning 403. No password or genuine login token was required. The test uses a bounded payload; disk exhaustion was not attempted. Request completion normally cleans temporary files in a real Go HTTP server, but that does not prevent memory/disk pressure during concurrent in-flight requests.

**Impact:** an attacker can submit large bodies to the Go process and consume resources even though they cannot publish content. A same-origin header does not stop a custom HTTP client. Any Cloudflare body limit is independent of the missing application limit and was not verified.

**Fix:** apply a small total limit, e.g. 16 KiB, at the beginning of login handling; only accept `application/x-www-form-urlencoded`; explicitly parse and handle errors; return 413 for oversized input and 415 for unsupported media types. Bound username/password lengths. Enforce a corresponding edge limit and request rate policy.

**Acceptance:** chunked and declared-length oversized requests stop reading at the bound, multipart login is rejected before parsing files, and legitimate login still succeeds.

### F02 — High: concurrent logins bypass the attempt budget and multiply Argon2 resource use

**Location:** `internal/handlers/admin.go:208–231`; `internal/auth/password.go:15–21`; login queries in `internal/db/queries.sql`.

The flow counts failures, then computes Argon2id, then records a failed attempt. These operations do not reserve a login attempt atomically. There is no separate concurrency limit on password verification. Each normal verification uses about 64 MiB for Argon2, plus overhead. The limit is per IP only, and recording a failure silently ignores database errors.

**Reproduction:** after four recorded failures, two simultaneous requests both returned 401 and produced six recorded failures. Both passed the threshold that should have allowed only one more attempt. This is a logical race, so a clean Go race-detector run does not refute it. The reproduction uses only two concurrent requests and is scheduling-dependent.

**Impact:** more guesses and expensive password computations than intended, with potential service memory/CPU exhaustion. This is not a password bypass; a correct password remains necessary to obtain a session.

**Fix:** atomically reserve budget before password hashing, bound concurrent Argon2 work, handle limiter write failures, and add a bounded site-wide budget/backoff in addition to trusted-client-IP limits. Avoid an unlimited wait queue or a permanent account lockout that lets outsiders deny the owner access.

**Acceptance:** parallel requests cannot exceed the reserved budget; hashing concurrency stays below its configured cap; limiter failures fail closed; recovery after the throttle window works.

### F03 — Medium, deployment-dependent: client identity and TLS state trust arbitrary forwarded headers

**Location:** `internal/handlers/admin.go:64–65,253–263`; `Dockerfile:14`; README proxy example.

`clientIP` uses the first `X-Forwarded-For` value from any peer. `requestIsSecure` similarly trusts `X-Forwarded-Proto` without checking the connecting proxy. A blocked direct client can choose a new IP header and get another password attempt.

**Reproduction:** after five failures and a 429 from one TCP peer, adding a different `X-Forwarded-For` produced 401 from that same peer. This is confirmed at the application boundary, **not confirmed through the deployed Cloudflare/Caddy chain**.

The live site is behind Cloudflare. Caddy's default reverse proxy discards incoming forwarded values, which can mitigate spoofing; if Caddy sees Cloudflare as its client without a configured trusted-proxy chain, it can instead collapse unrelated visitors into the same edge IP's login budget. The active Caddy configuration and origin firewall were not inspected. See [Caddy's header trust documentation](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#headers).

**Fix:** only consume forwarded identity from explicitly trusted immediate peers, validate the chain from the trusted end, and document Cloudflare-to-Caddy-to-Go handling. Keep the Go listener on loopback; block direct origin bypass of Cloudflare protections. For production, require the canonical HTTPS origin and secure cookies independently of arbitrary client headers.

**Acceptance:** direct forged headers do not change client identity or TLS decisions; genuine proxied clients remain distinct; the Go port is inaccessible externally. The live login cookie was already observed with Secure, HttpOnly, and SameSite=Strict.

### F04 — Medium: changing the admin password leaves old sessions authorized

**Location:** `internal/handlers/admin.go:96–150,242–249,266–269`; `cmd/server/main.go:33`.

Sessions are validated only by their database token hash and seven-day expiry. They are not tied to a credential version. Password-hash changes and process restarts do not invalidate them; logout deletes only the current session and ignores deletion errors.

**Reproduction:** sign in, construct a new server using the same database but a different password hash, and replay the original cookie: the dashboard still returns 200.

**Impact:** a previously stolen session can retain full write access after the owner changes the password. This requires prior session compromise; it is not an anonymous entry point.

**Fix:** bind sessions to a credential generation/fingerprint and reject old generations, provide a revoke-all operation, and treat failed logout invalidation as a failure. Document an incident procedure to revoke all sessions and pending OAuth state when rotating credentials. Consider a shorter admin lifetime and remove expired session/OAuth rows periodically.

**Acceptance:** password rotation immediately invalidates old cookies after restart, new login works, and revoked cookies cannot perform any write.

### F05 — Medium: missing explicit admin cache policy and browser security headers

**Location:** `internal/handlers/routes.go`, `internal/handlers/admin.go:44`; `internal/views/layout.templ`, `internal/views/admin.templ`.

The app emits no admin `Cache-Control: no-store`, CSP, frame restriction, Referrer-Policy, or HSTS. Local authenticated pages and live home/login responses confirmed the absence. The live login response currently reports Cloudflare `BYPASS`; **no cached authenticated-content leak was demonstrated**. The homepage is cacheable for 28,800 seconds, so explicit exclusions matter.

**Impact:** sensitive admin HTML/CSRF tokens have no application-level storage prohibition; there is no explicit anti-framing protection or CSP containment for a future injection. SameSite=Lax sessions already constrain cross-site iframe authentication, so absence of frame protection alone is not proof of cross-site authenticated clickjacking. Same-site framing remains relevant. HTTP redirect works, but HSTS is absent.

**Fix:** set `Cache-Control: no-store` across all `/admin` responses, including redirects/errors; configure an explicit Cloudflare bypass for `/admin` and `/admin/*`, and never cache authenticated responses. Add `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, and an appropriate referrer policy. Roll out HSTS after checking affected hosts. Build a CSP with `base-uri`, `object-src`, `form-action` and script restrictions; existing inline scripts/handlers must be externalized or handled deliberately rather than blindly adding a policy that breaks the gallery/editor.

**Acceptance:** verify headers at both app and public edge, prove admin responses cannot be shared between two sessions, and exercise login, Markdown preview, upload, and gallery navigation with CSP enabled.

### F06 — Medium: deployed build configuration is behind security fixes

**Location:** `go.mod:3,56`; `.github/workflows/ci.yml:49–52`; `Dockerfile:3`.

CI selects the exact Go version from `go.mod` (`1.26.5`). Scanning for Linux ARM64 with that version reports six standard-library symbol advisories plus two in `golang.org/x/text@v0.38.0`. The Go findings list fixes in 1.26.6; the two `x/text` findings are both addressed by v0.41.0. Use a currently supported patched toolchain, with those versions as the minimum for these specific findings. Updating the host's Go installation alone will not fix a workflow that still selects the old version.

| Symbol-level advisory | Component | Context and limits |
| --- | --- | --- |
| [GO-2026-6629](https://pkg.go.dev/vuln/GO-2026-6629) | x/text/secure/precis | Scanner path is through DBOS → PostgreSQL SCRAM; SQLite branch returns before that path. Advisory concerns Nickname profile; public exploit not established. |
| [GO-2026-5970](https://pkg.go.dev/vuln/GO-2026-5970) | x/text/unicode/norm | Reported paths similarly originate through DBOS/PostgreSQL; not demonstrated reachable by this app's visitors. |
| [GO-2026-6218](https://pkg.go.dev/vuln/GO-2026-6218) | net/url | URL resolution through outbound Flickr HTTP redirects and schema setup; attacker-selected outbound destinations are not exposed by routes. |
| [GO-2026-6090](https://pkg.go.dev/vuln/GO-2026-6090) | crypto/tls | Outbound HTTPS exists; inbound public TLS is terminated outside this Go process. |
| [GO-2026-6089](https://pkg.go.dev/vuln/GO-2026-6089) | net/http | Requires unencrypted HTTP/2 support; app does not explicitly enable it. Symbol reachability alone is insufficient. |
| [GO-2026-6088](https://pkg.go.dev/vuln/GO-2026-6088) | encoding/xml | Conservative trace includes Fuego's unused premade login/XML reader; app's login uses forms and RSS only encodes XML. |
| [GO-2026-5972](https://pkg.go.dev/vuln/GO-2026-5972) | encoding/asn1 | Indirect parsing/crypto paths; no public arbitrary ASN.1 input route identified. |
| [GO-2026-5026](https://pkg.go.dev/vuln/GO-2026-5026) | net/http IDNA behavior | Outbound client path; no demonstrated hostname-authorization bypass in this app. |

The scan also lists package-only `GO-2026-6091`, `GO-2026-5942` and module-only `GO-2026-6355`, `6354`, `6303`, `5932`. These must not be reported as six additional proven runtime exploits. In particular, updating `x/crypto` does not imply the app's Argon2 use was vulnerable to its SSH advisories.

**Fix:** update the toolchain and affected modules with compatibility tests, add pinned `govulncheck` scanning to CI and a scheduled check, and scan the actual release binary. Reassess remaining findings with documented reachability, especially advisories without a published fix. Fuego/DBOS transitively include code not used by this SQLite deployment.

**Acceptance:** production build metadata proves the patched versions; scans pass or have explicit narrowly justified exceptions; application and migration tests pass on Linux ARM64. No dependency changes were made during this audit.

### F07 — Medium, scale-dependent: public requests load the entire photo catalog

**Location:** `internal/flickr/store.go:229–361`; `internal/handlers/pages.go:49–63,94–138`.

Pagination slices an already-loaded gallery. The homepage's random photo and individual photo/modal lookups also load every matching photo. Thus inexpensive anonymous requests can trigger work proportional to the whole catalog; even nonexistent photo IDs perform the full load. Journal/RSS similarly fetch all published posts. Cloudflare caching helps repeated cache hits but does not bound origin work for misses and uncached routes.

**Impact:** resource amplification as the catalog grows. This is source-confirmed complexity, not a measured production outage or throughput claim. No load test was run on the public service.

**Fix:** apply pagination in SQL, select individual/adjacent/random photos without materializing all metadata, bound/cache public render work, and define origin request/concurrency limits. Decide explicit pagination/feed limits for journal growth.

**Acceptance:** disposable large-catalog tests show bounded rows/materialized bytes for a page or photo lookup, including nonexistent IDs. Confirm behaviour at the CDN and origin separately.

### F08 — Low: internal database errors reach public HTML responses

**Location:** `internal/handlers/pages.go:39–45`; `cmd/server/main.go:88–90`; Fuego default error serialization.

**Reproduction:** removing `site_settings` only in a disposable test database caused `/about` with `Accept: text/html` to return `get site settings: SQL logic error: no such table: site_settings (1)` to the client. Fuego's default HTML error path forwards arbitrary error strings.

**Fix:** provide a generic public 500 response, retain detailed server-side logs with a request ID, and preserve intentionally safe 4xx messages. Ensure untrusted text can never become raw HTML in an error response.

**Acceptance:** controlled database failures reveal no schema, filesystem, upstream credential, or SQL details for HTML, JSON and text clients.

### F09 — Low: RSS origin is derived from unvalidated Host and ignores proxy HTTPS

**Location:** `internal/handlers/pages.go:202–215`.

The feed constructs URLs using `r.Host` and `r.TLS`. At a TLS-terminating proxy `r.TLS` is nil. A local request with `Host: attacker.invalid` produced attacker-origin links. Whether an attacker can poison a shared production cache through this depends on edge host validation/cache keys and was not established. XML encoding prevents this from being a raw XML injection.

**Fix:** validate and use one canonical `PUBLIC_BASE_URL`, currently `https://imaginarymakings.dev`, for feed and OAuth URLs; reject unexpected production hosts. Update the README's old `new.imaginarymakings.dev` examples.

**Acceptance:** the feed always uses the canonical HTTPS origin regardless of incoming Host/forwarding headers, and OAuth callbacks use the current domain.

## Deployment, CI, and remaining verification

The checked-in systemd unit uses a dedicated unprivileged account, strict filesystem protection, no-new-privileges, private temporary/device namespaces, and a narrow writable data directory. The Docker runtime is non-root/distroless. These are useful controls, but deployment files are not evidence that the current host is actually configured that way.

The self-hosted deploy job only runs after CI on a push to main; pull requests use a hosted runner. Its helper validates revision syntax, installs into root-owned release paths and restarts a dedicated service. Nonetheless, the runner is an intentional authority to deploy arbitrary application code and thereby read/write the application's data and environment. Narrow sudo access does not make a compromised deployment runner harmless. Protect main/workflow changes and isolate the runner from unrelated repositories/jobs.

Concrete hardening backlog:

- Set explicit CI `permissions: contents: read`, disable persisted checkout credentials where unnecessary, pin actions to full reviewed SHAs, and verify downloaded build-tool/HTMX checksums. Current tags and curl downloads have no independent integrity check.
- Isolate the deploy runner and restrict its runner group/repositories; build on an isolated runner and deploy a verified artifact where practical. Review branch protection, GitHub account MFA and production environment rules. These settings were not accessible from source.
- Harden the root deploy helper against mutable staging/symlink races using a root-owned verified staged copy and explicit path/ownership validation. Current final-file checks are not an immutable snapshot, and writable ancestor directories remain trusted. No root-code-execution exploit was demonstrated.
- Add service memory/task limits after measuring normal workloads, filesystem/disk monitoring, request/429 alerts, and tested consistent SQLite/WAL backups. Verify restore and key recovery without using live user data.
- Return 404 for unknown paths by using an exact home route; the current `/` pattern serves home for nonexistent paths. This explains the harmless 200 responses on `/.env` etc. Disable public OpenAPI/Swagger if not needed; neither it nor static directory listing currently exposes admin authorization bypasses.
- Exclude `/healthz` from edge caching. The live response advertises an eight-hour cache lifetime, so the public endpoint is unsuitable as a fresh health probe. The deploy helper's loopback probe bypasses that CDN cache.
- Validate Flickr URLs before casting them to `templ.SafeURL`; they are currently trusted upstream data. Restrict to HTTPS and expected hosts, redact OAuth parameters from transport errors before storing/displaying errors, and consider sync serialization so disconnect cannot race with an in-flight cache replacement. These are defense-in-depth items, not demonstrated unauthenticated compromises.

**Still required for production sign-off:** inspect active Caddy configuration, Cloudflare SSL mode/WAF/cache/trusted-client settings, origin firewall/listening sockets, actual deployed binary/version, service permissions/resource limits, secret storage, and GitHub repository/runner controls. Public TLS and Cloudflare headers alone cannot establish origin isolation, Full (strict) TLS, or authenticated caching safety. No SSH access or authenticated admin browser session was used in this audit.

For this single-owner portfolio, putting `/admin` behind an identity-aware access gate with MFA or a private network would materially reduce exposure while retaining application authentication. Preserve the legitimate Flickr OAuth callback flow when configuring that gate. The Go-side fixes remain necessary.

## Reproduce and remediate

Run the opt-in checks with:

```sh
go test -tags securityaudit ./internal/handlers -run TestSecurityAudit -v
```

They intentionally confirm current weaknesses and should be converted into rejection/regression assertions when the fixes land; do not use their green result as a deployment security gate. No real credentials are required.

Implementation order, dependencies, and acceptance gates are in [the hardening plan](../plans/security-hardening.md).
